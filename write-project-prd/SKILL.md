# 撰寫專案 PRD

預設輸出 `docs/PRD.md`，描述「要做什麼」與「如何判斷完成」，不取代 TODO 或詳細架構／API／資料庫設計，不撰寫程式碼或開始實作。

## 內容與更新

先完整讀取既有 PRD，按需要查閱目前明確指示、相關文件、程式碼及測試。保留有效需求與人工內容，只更新受影響部分；無法判定的矛盾列為待確認。

- 區分已確認、規劃中與待確認；未實作不代表需求失效，宣稱已實作須有證據。
- 功能需求使用穩定 `FR-001` 等 ID，不任意重新編號或重用已刪除 ID。
- 驗收條件描述可觀察結果與必要邊界行為，不指定實作方法。
- 只記錄已知限制及非功能需求，不臆測 KPI、數值、工時或技術偏好；不加入任務勾選框、逐檔實作步驟或空章節。
- 保留必要來源、改作關係與引用範圍；不把普通相依套件當成改作來源。
- 缺少關鍵資訊才詢問；足以產生可用初稿時先整理，將其餘缺口列入待確認。
- 關鍵需求缺口或矛盾需使用者決定時，優先使用 `request_user_input` 提供具體選項與自由輸入；工具不可用或不允許該用途時改用對話。未回答的必要決策維持待確認，不自行定案。

## 核心框架

可沿用既有合適章節名稱，至少涵蓋概述、問題或目標、範圍／非目標、功能需求與驗收條件：

```markdown
# 產品需求文件

## 專案概述
## 目標與非目標
## 功能需求

### FR-001：功能名稱
**說明：** 功能要達成的結果。
**驗收條件：**
- 可觀察且可驗證的結果。

## 驗收條件
```

非功能需求、使用情境、限制、風險、待確認及參考來源等依實際需要加入，不建立空章節或殘留模板文字。

## 私有邊界

寫入前檢查 `.gitignore` 及 PRD 的 tracked／staged 狀態；有可用 upstream 或指定推送目標時也核對本機 outgoing commits，無法判定則回報限制。無明確公開授權而已 tracked、staged 或待推送時停止並回報，不自行取消追蹤或改寫歷史。

預設保留獨立規則 `docs/PRD.md`，缺少時增量補上並核對忽略狀態，不覆寫其他規則。`.gitignore` 不會解除既有追蹤或清除歷史。公開特定 PRD 須有明確指示且先檢查商業規劃、個資、安全及引用；一般「全部上傳」不構成授權。文件不保存憑證或不必要個資。

## 完成標準

需求一致、ID 穩定、可驗收、無臆測、隱私正確。回報主要變更、待確認與追蹤風險；不自動更新 TODO／README，不暫存、提交或推送。

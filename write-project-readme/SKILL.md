# 撰寫專案 README

`README.md` 使用台灣繁體中文並作為語意基準，`README.en.md` 使用自然技術英文；兩份皆可從缺失狀態建立，PRD 不是前提。

## 查證與內容邊界

先完整讀取兩份既有 README，按本次內容查閱相關程式碼、設定、測試、文件、版本及可靠發布資料；不每次全面掃描無關 CI／Release。現行程式碼與設定證明已實作行為，矛盾須查證或回報，不能把使用者期待或 PRD 規劃當成現況。

必要的專案用途、名稱、來源關係或公開範圍無法查證時，優先使用 `request_user_input` 提供具體選項與自由輸入；不可用或不允許該用途時改用對話。未回答時不虛構或推定公開意圖；不為裝飾或可省略的次要內容提問。

- 保留正確的人工內容、品牌、警告、致謝與有效自訂章節，增量修正受影響部分。
- 命令取自實際 scripts、套件管理器與設定；版本保留來源支持的精度與範圍，不用本機版本或無依據的 latest 推斷支援。
- 不虛構功能、平台、效能、安全保證、測試、Release、下載連結、授權或上游關係；必要資訊無法確認才詢問，其餘省略，不留空章節或模板文字。
- TODO、PRD、HANDOFF 與未公開文件只作背景，不在公開文件提及其存在、路徑或連結，也不摘要其內部 TASK／FR／Phase、驗收矩陣、排程、商業或交接脈絡。公開敘述須能由程式碼、測試、設定或公開資料獨立支持並有讀者價值，不揭露開發者私人事項或未公開後續規劃。
- 不寫入真實憑證、個資、私人路徑或端點；設定範例使用預留值。公開特定私有內容須有明確授權並先檢查，不以 README 繞過隱私邊界。
- 使用者完成安裝所需的 `.env`、本機設定等可說明用途、建立方式與預留值；文件主題本身需要說明 Git 忽略規則時也可列必要路徑。這些例外不授權揭露真實內容或列出無關私有文件。

## 讀者與內容取捨

- 面向一般使用者與新開發者，優先說明用途、主要特色、如何開始及必要限制，避免內部開發紀錄式敘述。
- 功能介紹挑選最重要或具辨識度的已驗證能力，以簡潔條列描述價值與行為，不羅列所有功能、控制項或實作細節。
- 架構、初次安裝、參數與其他章節過長時，依讀者需求考慮拆成獨立公開文件；README 保留必要摘要、最短可用起點及連結。拆分文件須有獨立用途與完整背景，不製造零碎或重複內容。

## 更新價值

- 功能新增、調整或移除時，先判斷是否影響讀者理解、使用方式、主要能力、相容性或重要限制，再決定是否新增說明；不把每次修改寫成一項功能或開發紀錄。
- 已有說明時優先修改原文；不值得新增條目仍須修正或移除過時資訊，包含失效命令與已移除功能。

## README 結構

每份 README 至少包含：

1. 已驗證的專案標題
2. 說明用途、目標情境與主要價值的簡短描述
3. 另一語言版本的相對連結

README.md 使用 [English](README.en.md)；README.en.md 使用 [繁體中文](README.md)，位置與格式應一致。

只加入有證據且對讀者有用的章節：

| English | 繁體中文 | 加入條件與要點 |
|---|---|---|
| Overview | 專案簡介 | 短描述不足，或需交代背景、使用者、情境、目標及重要上游關係時 |
| Features | 功能特色 | 精選重要或具辨識度的已驗證能力，以簡潔條列描述讀者價值與行為，不列完整功能清單 |
| Demo | 展示 | 僅限已存在且權利明確的展示、截圖、GIF 或影片；儲存庫資源優先用相對路徑並檢查大小寫 |
| Requirements | 系統需求 | 已驗證的 OS、runtime、工具、外部服務或硬體條件；必要時區分執行與開發需求 |
| Technology Stack | 使用技術 | 只列有助理解、執行或開發的核心技術；保留可驗證版本及範圍，不列所有間接相依套件 |
| Installation | 安裝 | 可重現且順序正確；使用 lockfile 對應套件管理器、實際 scripts、路徑與必要建置／設定步驟 |
| Configuration | 設定 | 只記錄由範例、Schema、程式碼或正式文件支持的設定；標示必要性並以預留值表示機密 |
| Usage | 使用方式 | 提供符合實際行為的 CLI、UI、API 或函式庫範例；詳細內容連結至 docs/ |
| Development | 開發 | 僅記錄與一般使用不同且已驗證的開發、建置、lint、格式化、除錯或本機服務流程 |
| Project Structure | 專案結構 | 確實有助理解時，只列重要路徑，不列相依套件、輸出、快取或細碎檔案 |
| Testing | 測試 | 實際存在測試或測試指令時；不得推測覆蓋率或完整性 |
| Documentation | 文件 | 只連結存在且適合公開的文件；不列私有、被忽略或未發布文件的名稱、路徑與連結，必要設定與忽略規則教學例外依前述邊界 |
| Release | 發布版本 | 有 tags、Release、changelog、發布設定、產物或 workflow 等正式證據時 |
| Roadmap | 開發藍圖 | 僅在使用者明確要求公開規劃且通過內容檢查時加入；不複製私有 TODO 或內部追蹤，預設不列後續計畫 |
| References | 參考與致謝 | 存在已驗證的參考、改作、移植、fork、素材、模型、資料集、論文或其他來源時 |
| Contributing | 貢獻 | 有正式文件、模板、流程或使用者指示時；不得虛構 branch、commit、PR 或 review 規則 |
| License | 授權 | 有授權檔、套件中繼資料或使用者指示可驗證時；否則通常省略 |

標題與短描述已足夠時，不必另建「專案簡介」。架構、API、資料庫與部署細節通常留在 docs/，README 只保留必要摘要與入口。徽章不是獨立章節；僅在目標和值均可驗證且有用時精簡加入。

## 引用、授權與發布

實質 fork／衍生／改作須在專案簡介前段準確揭露並連結來源，於「參考與致謝」記錄關係、主要修改與授權／引用義務。精確區分 fork、改作、啟發與普通相依，兩語措辭強度一致；不得因結構相似推斷改作，也不弱化已知上游關係。

授權依既有檔案或明確指示，不自行選擇、建立或宣稱 License；未確認的必要授權義務需回報。Release 的版本、日期、產物與狀態須有證據，不把預設分支或 pre-release 寫成穩定發布。

## 更新與驗收

以同一份已查證事實更新中文並同步英文。兩語章節涵蓋、功能狀態、指令、版本、URL、警告、來源與授權須等價；有效的單語資訊先查證再同步。不強制重排有效自訂內容。

完成時核對四個面向：**事實正確、連結／命令可用、雙語同步、沒有私有資訊洩漏**，並確認內容精簡、有讀者價值，拆分文件有有效入口，既有說明沒有過時。安全可行時驗證命令，不修改程式來迎合 README；只有實際成功執行才回報「已測試」。

回報主要變更、重要未決事項與驗證限制。不實作 docs 全面分類或 Git 交付，不刪無關檔案、暫存、提交或推送。
